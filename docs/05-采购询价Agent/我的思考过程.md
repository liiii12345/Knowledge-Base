# 05 · 我的思考过程

> **先把角色边界写清楚**：这套询价规则的初版不是我写的。我拿到的是一份已经在用的规则文档，我做的是四件事——逆向出它为什么长这样（需求溯源）、跑数据验证它到底有没有被执行（评测设计）、把有问题的地方改掉（缺陷修复）、用脱敏数据复现成一份可公开演示的项目。**下面写的是我的判断，不是从零设计。**

## 一、先反推：这份规则是被什么事打出来的

拿到规则文档，我没先照着做，而是先问「它为什么写成这样」。几处痕迹很说明问题：

| 痕迹 | 反推出的失效模式 |
|---|---|
| 「最高优先级」写在全文最前，还特意强调「含思考过程」 | 模型在推理阶段就跑偏过，不是输出阶段才错 |
| 出现具体数字「757 条」并贴出错误输出原文 | 留的是一次真实事故的现场，凭空编不出来 |
| 同一条禁令重复 5 遍以上，还注明「接口保留但 Agent 不得调用」 | 反复调、反复出事，最后只能靠重复压制 |
| 34 个省级行政区硬编码进文档 | 曾让模型自己判断地区，结果不稳定，只能退回到常量表 |

**结论：这份规则是事故驱动的补丁堆，不是架构设计的产物。** 按事故发生顺序往上叠，不是自顶向下分层。这个判断决定了后面的动作——我要做的不是继续往上叠补丁，而是**分清哪些约束该留在提示词、哪些该下沉到代码、哪些根本不该由 Agent 承担**。

## 二、分层：约束作用在哪一层，就该在哪一层解决

把规则按「作用于模型的哪一层」重新归类，分出三层：

| 层 | 例子 | 该谁负责 |
|---|---|---|
| 推理层（CoT） | 术语、输出口径 | 留在提示词 |
| 工具调用层 | 调用次数、禁止重试、无意图不检索 | **下沉到代码 + 评测验证** |
| 数据层 | 错别字、俗称映射 | **不该由 Agent 承担，是知识库建设** |

第一条判断：**「调用 ≤ 5 次」「失败不重试」这类规则写进提示词没法保证执行**。遵守率随模型状态浮动，出事时你无法证明是规则没写清还是模型没遵守。我把它落成代码里的硬分支，再用评测逐维比对——评测是这些约束唯一的验收口径。

第二条判断：**统计必须交给服务端**。原规则要求「模型直接归纳 757 条数据的均价与区间，禁止写脚本」。近千条数据的均值和分位数是确定性算术，让用户拿去做决策的数字去赌模型的算术能力，这个取舍我不认同。**「禁止写脚本」的初衷是防止 Agent 跑偏成一堆临时文件，正确做法是把聚合做进检索接口**，而不是禁止工具后让模型硬算。

## 三、验证：先做评测集，再看效果

没有评测集就没法证明改动有效，所以我先标了 40 条用例——每条人工标注「正确的过滤条件是什么」，再由标注条件直接查库得到 oracle 结果作为对照组。对照组存在的意义是：**把「查得对不对」和「召回得准不准」两个问题分开**。

第一轮跑完 92.5%，暴露三个失效模式，我按层归因：

| 用例 | 现象 | 归因 | 处置 |
|---|---|---|---|
| `上个月广东省垃圾袋价格` | 时间词没覆盖，漏掉时间过滤 | 解析层 | 已修：补相对时间换算 |
| `沪市静音滑轨价格` | 地区简称没映射，地区维度丢失 | 解析层 | 已修：补简称映射 |
| `抛柚砖什么价`（错别字） | 召回为 0，退化成追问 | **知识库层** | **不在检索层解决** |

前两个改成 97.5%。第三个我明确留着——「抛柚砖」→「抛釉砖」靠的是别名表，属于数据建设。**用提示词补数据缺陷，是这类项目最常见的内耗。**

另外还修了两个自己写出来的 bug：产品词没从剩余片段剥离，导致「厂名+产品」连写时供应商维度丢失；规格正则顺序错，`A4-70g` 被截成 `70g`。

## 四、一个刻意的妥协

模糊召回我用字符 bigram + 余弦，不是真向量模型。理由是保证**零依赖、可重放**——任何人在任何机器上跑评测都能得到完全一致的分数，否则无法归因。真实环境换 embedding 模型时，`matcher.py` 是唯一要替换的模块，接口不变。

**可复现优先于效果上限**，这是我在这类演示项目上的一贯取舍。
