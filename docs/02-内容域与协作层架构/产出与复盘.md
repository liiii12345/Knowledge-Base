# 02 · 产出与复盘

## 产出物

| 产出 | 内容 | 解决的争议 |
|---|---|---|
| 架构分层图 | 内容层（3 个域）+ 协作层（2 个模块）的从属关系 | "协作功能该放在哪" |
| 实体关系定义 | 内容域 × 协作层的引用方式（引用而非复制） | 跨层数据怎么走 |
| 权限矩阵 | 内容权限（谁能看内容）与协作权限（谁参与事）分离 | 两套权限打架 |
| 粒度规范 | 单文件 / 多文件目录两档 + 混附件追加规则 | 挂载到底做多少层 |
| 视图设计 | 「我的任务」（个人视角）+「专项协作」（事务视角） | 用户从哪进入协作 |

## 结果

- 该架构作为该产品一次大版本改版的基础方案被采纳，后续功能规划都挂在这套分层上（覆盖知识库、业务数据、云文档等多个产品模块）
- 权限分离后，"跨部门共享要不要管理员审批"这类问题有了统一判定口径（内容跨域共享走申请，协作参与者由发起人决定）

## 复盘：如果重来

1. **别等耦合了才分层**：早期把协作塞进知识库，是因为"顺手"。等三类内容都长出来再拆，返工成本远高于一开始分好层——**架构债要早还**
2. **视图比功能更能定架构**：我先纠结"协作层该有几个模块"，后来改成先想用户从哪进来（我的任务 / 专项协作），模块划分反而一下清晰了。**先定入口，再定结构**
3. **跨平台内容坚持"引用不复制"**：外部云文档只保留链接与返回入口，不落地副本。短期看搜索体验差一点，长期省掉了内容同步、版本漂移、权限泄漏三个大坑
