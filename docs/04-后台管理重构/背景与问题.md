# 04 · 背景与问题

## 一句话

后台管理系统迭代到第三个年头，功能越加越多、入口越来越散——**这时候该做的是加法还是减法？**

## 场景

一个 ToB 内容产品的管理后台，长期使用后出现典型症状：

| 症状 | 具体表现 |
|---|---|
| 模块膨胀 | 管理项从最初的 3 类长到 6 类以上，分类之间边界模糊 |
| 找不到入口 | 同一个设置项在两个地方都能改，用户不知道该去哪个 |
| 长列表低效 | 知识库与业务数据列表动辄上百条，只能靠翻页找 |
| 操作要来回滚 | 顶部筛选、底部操作，长列表场景下反复上下滚动 |

## 真正的问题

不是"功能不够"，是**信息架构失序**：早期每来一个新需求就加一个管理项，加着加着，用户心智里的"后台是干什么的"被稀释了。

## 为什么值得做

后台是管理员每天都要用的高频场景，架构混乱的成本是**每天**在付的。重构这里，投入产出比远高于再做一个新功能。
