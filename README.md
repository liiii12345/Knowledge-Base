## 项目一 · 需求拆解工作台

**把一堆零散业务诉求，收敛成"先验证哪一块"的结论。**

`tools/requirement-triage/index.html` — 单文件 HTML，**下载双击即用**，无需 npm、无需服务器、无需联网。

| 步骤 | 输入 | 输出 |
|---|---|---|
| 解析 | 粘贴需求清单（每行一条） | 自动拆字段 + 猜部门 |
| 打标签 | 点一下 | 需求类型（问答/处理/生产/协作/管理）+ 依赖能力 |
| 看分布 | 自动 | **纯问答 vs 需能力编排的占比**、能力依赖 Top、部门 × 类型交叉表 |
| 定验证域 | 四个维度各打 1-5 分 | 总分 + 建议（验内核 / 验边界 / 暂缓） |
| 导出 | 点按钮 | 台账 CSV、分析报告 Markdown、结构化 JSON |

**关键设计**：用关键词规则引擎而不是大模型——分类要可解释、可复现、可逐条人工修正。内置 41 条脱敏示例需求，跑出来是 29.3% 纯问答 / 70.7% 需能力编排。

## 项目二 · Tech Intelligence Daily Agent

**一条全自动科技情报日报流水线：多源采集 → 关卡校验 → 生成 11 板块日报 → 双渠道推送。**

零第三方依赖（全用 Python 标准库），`--demo` 模式离线跑通，出一份完整的 11 板块日报。

```bash
cd agents/tech-intel-daily
python -m unittest discover -s tests      # 10 个单元测试
python -m scripts.run_daily --demo        # 采集 → 验证 → 红线 → 生成 → 编码守卫
```

| 关卡 | 做什么 | 失败时怎么处理 |
|---|---|---|
| 新数据验证 | 今日目录存在 / 条目 >0 / 数据未过期 24h | **发通知并终止**，宁可不发也不推旧内容 |
| 质量红线 | 五条红线逐条检查（摘要字数、来源、链接、禁推断句式、YouTube 三要素） | 违规条目挡在正文外，写进附录并注明原因 |
| 编码守卫 | 扫描 Mojibake / `\xNN` 双重编码 / BOM | 终止发布 |
| LLM 降级 | 模型调用失败自动切模板合成模式 | 保证永远能出完整日报 |

日报 11 个板块：核心动态 / 今日速览（加热度）/ 今日金句 / 信息分层（⚡必看·📖速读·🔬深读）/ YouTube 播客 / Twitter 精选 / 趋势与关联 / 行动建议 / 待观察 / 数据看板（今日 vs 昨日）/ 推荐阅读。

**红线的关键：写在 prompt 里要求模型遵守是不够的，得有一层代码兜底**——这才是量产质量的保证。
8 次线上故障的完整复盘（中文乱码、yt-dlp 封禁、中文相对时间解析、静默失败推旧日报等）在 `docs/engineering-notes.md`。

## 项目三 · Procure-Pricer：采购询价 Agent

**一句口语的「XX 什么价」，转成对价格库的规范化查询——并且查得出来。**

零第三方依赖，三条命令跑通全流程：

```bash
cd agents/procure-pricer
python src/generate_mock_data.py                  # 25,920 条虚构价格记录，固定种子可重放
python src/cli.py "山东省东鹏抛釉砖近半年的采购价"
python eval/run_eval.py                           # 40 条标注用例，三方对照
```

| 环节 | 做法 |
|---|---|
| 意图门控 | 三情形判定：本无该维度意图 → 跳过；已被占用 → 不再下传；有意图 → 模糊召回择一 |
| 查价 | 单入口，先 count 再分支：EMPTY / TOO_MANY(≥1000) / LIST |
| 输出 | 服务端聚合（分位数 / TopN / 月度趋势），明细落 CSV，对话里只给结论 |

**为什么值得看**：不做门控的基线方案，**空结果率 97.5%**——Agent 太勤快，用户没提供应商它也要猜一个塞进去，结果几乎每次都查空。加门控后 97.5% 的查询能拿到结果。约束在这个场景里不是优化项，是可用性前提。

| 指标 | 门控方案 | 无门控基线 |
|---|---:|---:|
| action 一致率 | **97.5%** | 7.5% |
| 空结果率 | **7.5%** | 97.5% |
| 平均检索调用次数 | 2.08 | 2.00 |

两轮迭代（v1 92.5% → v2 97.5%），修的是地区简称与「上个月」时间解析；错别字这一类**明确不修**——那是别名表的事，不该用提示词去补数据缺陷。

> 数据 100% 由脚本生成，供应商与价格均为虚构，不含任何真实企业数据。

## 配套：方法论案例

上面三个项目的**思考过程**在这里。每个案例固定三件套：**背景与问题 → 我的思考过程 → 产出与复盘**。

| # | 案例 | 讲清楚的问题 |
|---|---|---|
| [01](docs/01-需求拆解与场景验证/) | 需求拆解与场景验证 | 几百条零散诉求，怎么收敛成"先验证哪一块"的结论（→ 项目一） |
| [02](docs/02-内容域与协作层架构/) | 内容域 × 协作层架构 | 知识库不该只是"网盘+聊天框"，架构层怎么取舍 |
| [03](docs/03-AI能力定位/) | AI 能力定位 | 七成需求要靠 OCR/问数/生成，不是纯问答 |
| [04](docs/04-后台管理重构/) | 后台管理重构 | 功能越多越乱，怎么用"减法"重建后台信息架构 |
| [05](docs/05-采购询价Agent/) | 采购询价 Agent | 一句口语提问到一次正确查询之间，哪些约束必须硬做、怎么验收（→ 项目三） |

前四个案例是一条线：**拆需求 → 定架构 → 定 AI 定位 → 定管理秩序**，后一步是前一步的必然结果。案例 05 是另一条线：能力定下来之后，Agent 的约束怎么落地成可验证的东西。
