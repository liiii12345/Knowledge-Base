# 需求溯源（脱敏版）

> 本文档只保留业务口径与方法论，不引用任何内部文档原文、系统名或人员姓名。

## 一、需求来源

原始需求来自某集团「招采成本」条线的 AI 需求收集，与价格相关的诉求集中在四条：

| # | 条线 | 诉求（脱敏转述） | 与本项目的关系 |
|---|---|---|---|
| 1 | 招采管理 | 采购询价：拿到供应商报价后，AI 自动到价格库里比对并做价格分析 | **主需求，本项目直接承接** |
| 2 | 招采管理 | 定价情况：按专业工程导出例年定标系数，并按地区分析 | 能力延伸 → 本项目的地区 + 时间维度 |
| 3 | 造价管理 | 审核过程中补充的材料价格需要横向对比（已审 vs 在审） | 同一价格能力池，**未实现** |
| 4 | 成本管理 | 从云端获取公开价格，用于调差测算 | 数据源不同，**不在范围内** |

第 1 条拆成两个动作：**查到价格**（检索）+ **做价格分析**（归纳与对比）。前者是本项目的核心，后者落到服务端的聚合与趋势输出。

## 二、业务约束（决定了技术选型）

| 约束 | 来源 | 对设计的影响 |
|---|---|---|
| 一线人员用口语提问，不会记规范名 | 需求描述 | 必须有模糊召回 + 规范值回填 |
| 单次查询可能返回上千条 | 库内数据量 | 必须有 count 阈值分支，明细落文件而非塞进对话 |
| 要「按地区、按例年」分析 | 需求第 2 条 | 地区做成常量枚举、时间必须支持相对换算 |
| 查询是高频动作 | 使用场景 | 严格限制调用次数，禁止失败重试与换词重试 |

## 三、需求与实现的对应关系

| 需求动作 | 实现 |
|---|---|
| AI 自动辨别 | `matcher.py` 模糊召回 → 择一回填规范值 |
| 价格库查询 | `query_engine.py` 单入口，包含匹配（contains）语义过滤 |
| 进行价格分析 | `summarize.py` 分位数 / TopN / 月度趋势 |
| 按地区、按例年 | `intent_parser.py` 省级常量 + 相对时间换算 |
| 导出相关信息 | LIST 分支生成明细 CSV |

## 四、未承接的需求与原因

| 需求 | 未承接原因 |
|---|---|
| 材料价格横向对比 | 需要跨批次对比接口，当前检索层只支持单次查询；列为后续项 |
| 报价偏高偏低判定 | 需要基准价/分位数定义，属业务规则，需与造价条线对齐口径后再做 |
| 云端取价 | 数据源不同（外部公开价格 vs 内部历史库），应独立立项 |
| 价格库本身建设 | 数据治理工作，Agent 是查询层不是供给层 |

## 五、一个容易被忽略的边界

同一批需求里还有一类「价格」诉求实际指的是**销售定价**（房屋售价合理性评审），与采购价完全不是一个数据域。归需求时按数据域划分，不要按关键词「价格」归并——否则会把两条无关产品线混成一个需求。
