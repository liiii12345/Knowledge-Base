# 设计取舍

## 1. 统计放服务端，还是让模型心算？

**选：服务端。**

原始方案写的是「模型直接归纳统计，禁止写脚本」。反对理由：近千条数据的均值、分位数属于确定性算术，交给模型的误差不可控，而这是用户唯一会拿去做决策的数字。让它「禁止写脚本」的初衷是防止 Agent 跑偏成一堆临时文件，正确做法是**把聚合做进检索接口**，而不是禁止工具后让模型硬算。

代价：检索接口多返回一组聚合字段，单次响应变大。相比数字错误，这个代价可以忽略。

## 2. 门控做成硬规则，还是交给模型判断？

**选：硬规则 + 评测验证。**

「用户没提供应商就不要查供应商」这类判断，写进提示词的遵守率取决于模型状态。本项目把它做成代码里的三情形判定（无意图 / 被占用 / 独立），并用评测逐维比对。

代价：规则维护成本转移到代码。但代码可以回归测试，提示词不能。

## 3. 产品词与供应商词连写时怎么切？

**选：先定位产品词跨度并剥离，剩下的才是供应商候选。**

「临沂市高新安泰纸业纸巾盒价格变化」如果整段当产品词，会同时丢掉供应商维度、并把厂名污染进物料描述过滤条件，结果是查空。先按规范品类名的**最长前缀**定位产品词（「纸巾盒」→「纸巾盒子」），剥离后「临沂市高新安泰纸业」作为供应商候选。

代价：依赖「用户说法是规范名的前缀」这一假设。错别字场景下会整体退化（见 README 已知缺口），这属于知识库覆盖问题。

## 4. 阈值怎么定？

| 维度 | 阈值 | 依据 |
|---|---|---|
| 品类召回 | 0.30 | 品类名短、区分度高，放宽以提高召回 |
| 供应商召回 | 0.42 | 供应商全称长且高度相似，放宽会大量误命中 |

阈值不做全局统一——这是从评测里「卫浴股份有限公司」被误匹配成电缆厂商这类 bad case 调出来的。

## 5. 明细为什么落文件而不是直接展示？

单次查询上限接近 1000 条，对话窗口展示明细既不可读也无决策价值。界面只给三件事：**命中条数、价格分布、主要构成**，完整明细走文件。同时也避免了「为了分析明细而让模型读文件」这一整类跑偏行为。

## 6. 为什么坚持单次查价、失败不重试？

查询是高频动作，一次失败重试就翻倍成本。更重要的是：**重试通常换不来新信息**。字段缺失、知识库无候选这类失败，重试多少次结果都一样。正确处置是明确告知「知识库未匹配到 XX」并结束，而不是反复试探。

代价：瞬时网络故障也不会重试。可接受——高频查询场景下一次失败由用户重发即可。

## 7. 最大的一处妥协

模糊召回用字符 bigram 余弦，不是真向量模型。原因是保证**零依赖、可重放**：任何人在任何机器上 `python eval/run_eval.py` 都能得到完全一致的分数。真实环境换成 embedding 模型后，`matcher.py` 是唯一需要替换的模块，接口不变。
