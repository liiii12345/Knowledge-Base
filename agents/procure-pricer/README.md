# Procure-Pricer：面向采购询价的检索式 Agent

> 把一句口语化的「XX 什么价」，转成对物料价格库的规范化查询，并给出可直接用于决策的统计结论与明细。
>
> **数据说明**：仓库内所有数据均为脚本生成的虚构样本（25,920 条），不含任何真实企业数据。供应商名、价格、地区分布全部由 `src/generate_mock_data.py` 随机生成，可无限重放。

---

## 30 秒跑起来

```bash
# 1) 生成脱敏价格库（约 4 MB，25,920 条）
python src/generate_mock_data.py

# 2) 直接问一句中文
python src/cli.py "山东省东鹏抛釉砖近半年的采购价"
python src/cli.py --debug "临沂市高新安泰纸业纸巾盒价格变化"   # 附带意图门控决策日志

# 3) 跑评测（门控方案 vs 无门控基线，40 条用例）
python eval/run_eval.py
```

零第三方依赖，Python 3.9+ 即可运行。

## 这个项目解决什么问题

企业采购/造价人员想问价格时，说的是人话：

> 「山东省东鹏抛釉砖近半年的采购价」
> 「临沂市高新安泰纸业纸巾盒价格变化」
> 「万邦陶瓷抛釉砖价格」

但价格库认的是规范数据：分类、供应商全称、规格型号、品牌、地区、日期范围。两者之间隔着三道坎：

| 坎 | 具体表现 | 本项目的处理 |
|---|---|---|
| 词对不上 | 用户说「纸巾盒」，库里叫「纸巾盒子」；说「沪市」，库里是「上海市」 | 向量模糊召回 + 规范值回填 |
| 维度会编 | 用户没提供应商，Agent 却硬塞一个 filter，结果查空 | 意图门控（A/B/C 三情形判定） |
| 结果不好用 | 一次查回上千条，聊天窗口塞不下，也不该塞 | 服务端聚合 + 明细落文件，界面只给结论 |

最要命的是第二道坎：**无门控的 Agent 会把每个维度都填满**。评测里基线方案（不做门控、用户原话直传）的**空结果率高达 97.5%**——几乎每次查询都查了个寂寞，还白白消耗调用。

## 核心链路

```
用户问句
  │
  ├─ 1. 确定片段 ── 地区(常量映射) / 品牌(词表) / 规格(正则) / 时间(相对换算)
  │                                                     ↑ 不消耗检索调用
  ├─ 2. 剩余片段 → 定位产品词跨度 → 剥离后得到供应商候选
  │
  ├─ 3. 意图门控
  │      A. 本无该维度意图  → 整维跳过，禁止伪造
  │      B. 分词已被占用    → 不再向下一维传递
  │      C. 有意图且未占用  → 模糊召回 + 择一
  │
  ├─ 4. 单次查价：count → EMPTY / TOO_MANY(≥1000) / LIST 分支
  │
  └─ 5. 输出：统计归纳 → 趋势迷你图 → 明细文件
```

关键约束：**整任务检索调用 ≤ 5 次（实测均值 2.08），查价只调 1 次，失败不重试、不换词重试。**

## 评测结果

40 条用例，每条人工标注「正确的过滤条件」，由标注条件直接查库得到 oracle 结果作为对照组。

| 指标 | gated（本方案） | naive（无门控基线） |
|---|---:|---:|
| action 一致率 | **97.5%** | 7.5% |
| 空结果率 | **7.5%** | 97.5% |
| 平均检索调用次数 | 2.08 | 2.00 |
| 门控合规率 | 97.5% | — |
| 过滤条件准确率 | 97.5% | — |

### 两轮迭代

| 轮次 | action 一致率 | 过滤条件准确率 | 门控合规率 | 本轮修复 |
|---|---:|---:|---:|---|
| v1 | 92.5% | 92.5% | 97.5% | — |
| v2 | **97.5%** | **97.5%** | 97.5% | 地区简称（沪/粤/鲁…）、`上个月` 时间解析 |

v1 暴露的三个失效模式：

| 用例 | 问题 | 归因 | 处置 |
|---|---|---|---|
| `上个月广东省垃圾袋价格` | 时间词未覆盖，漏掉时间过滤 | 解析层 | v2 已修 |
| `沪市静音滑轨价格` | 地区简称未映射，地区维度丢失 | 解析层 | v2 已修 |
| `抛柚砖什么价`（错别字） | 分类召回为 0，退化为追问 | **知识库层** | 已知缺口，见下 |

最后一类不是 Agent 逻辑问题——「抛柚砖」→「抛釉砖」靠的是知识库别名表，属于数据建设范畴，改 prompt 解决不了。这个区分本身是项目结论之一：**别用提示词去补数据缺陷**。

### 已知缺口

- 错别字 / 俗称（「马桶」→「连体坐便器」）需要维护别名表，不在检索层解决
- 单次查询不支持多值（「铜芯电缆和铝合金电缆」只取其一）
- 「报价是否偏高」这类判定需要基准价/分位数，当前只给区间与均价
- 横向对比（已审 vs 在审批次的价格对比）尚未实现

## 设计上的三个判断

**1. 统计交给服务端，不交给模型。**
原始方案硬性要求「模型直接归纳 757 条数据的均价与区间，禁止写脚本」。近千条数据的心算误差不可控，这是拿提示词约束去赌算术能力。本项目改为检索层直接返回 `count / min / max / avg / 中位数 / P25 / P75 / TopN / 月度序列`，模型只负责措辞。

**2. 硬约束必须可自动验证。**
「调用 ≤ 5 次」「失败不重试」「无意图不 match」这些规则写进提示词无法保证执行。本项目把它们落成评测指标：调用次数直接统计、门控结果逐维比对、失败用例可回归。评测是这些约束唯一的验收口径。

**3. 区分「模型问题」「解析问题」「数据问题」。**
评测暴露的三个失效模式分属三层，处置方式完全不同。混在一起处理的结果就是不停加提示词，越加越长、越加越难维护。
