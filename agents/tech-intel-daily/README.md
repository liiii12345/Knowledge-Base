# Tech Intelligence Daily Agent

一个**可复现的科技情报日报流水线**：抓取信源 → 筛掉噪音 → 结构化抽取 → 渲染成能直接转发给团队的日报。

不是"让 AI 帮我写日报"，是**把日报的判断标准固化成可执行的东西**。

---

## 三分钟跑通（零配置、零依赖、零成本）

```bash
git clone https://github.com/liiii12345/Knowledge-Base.git
cd Knowledge-Base/agents/tech-intel-daily
python scripts/run.py --demo
```

跑完看 `output/daily-<今天日期>.md`。全程不联网、不需要 API key。

接自己的信源：

```bash
cp sources.example.yaml sources.yaml   # 填你的 RSS / Atom 地址
python scripts/run.py
```

用大模型做抽取（比规则准，但要花钱）：

```bash
export OPENAI_API_KEY=sk-xxx
python scripts/run.py --llm            # 也支持任何 OpenAI 兼容接口，见 --base-url
```

## 它到底在解决什么问题

每天看科技新闻的人不缺信息，缺的是**判断哪些信息值得占用团队注意力**。这个项目的取舍全部集中在这一件事上：

| 环节 | 常见做法 | 这里的做法 |
|---|---|---|
| 筛选 | 关键词订阅，来什么看什么 | **先定丢弃标准**：营销稿、纯观点、重复报道直接出局 |
| 分级 | 按热度排 | 按**对决策的影响**分 P0/P1/P2，P0 是"48 小时内要决策" |
| 写作 | 让模型自由发挥 | 硬约束：禁用"革命性/颠覆/划时代"；事实与判断分离，字段级规定 |
| 可信度 | 不标注 | 输出 `confidence`，低于 0.6 单独进「待核实」，不混进结论 |
| 透明度 | 只给结论 | 日报末尾列出**今天筛掉了什么、为什么** |

## 为什么规则模式和 LLM 模式并存

| | 规则模式（默认） | LLM 模式（`--llm`） |
|---|---|---|
| 成本 | 0 | 每跑一次几毛钱 |
| 可复现 | 完全一致 | 有随机性 |
| 准确率 | 够用，但会漏 | 明显更准，尤其长句和隐含语义 |
| 用途 | **跑通流程、自测、CI** | 日常生产 |

规则模式存在的意义不是省钱，是**让这条流水线的判断标准变成可读的代码**。改一条规则是改一个列表，不是改一段咒语。

## 已知问题与坑

1. **否定语境**：`"新闻稿未给出任何参数、价格、上线时间"` 会命中"参数/价格/上线"三个实质词，反而被判为有价值。已在 `effective_substance()` 里处理——否定词之后出现的实质词不计入。这是关键词方法的通病，遇到新写法还得补规则
2. **规则模式的 P0 判定偏保守**：只认"漏洞/补丁/安全/定价/下线"这组硬词，重大模型发布可能只判到 P1。要更准就用 `--llm`
3. **不处理付费墙与反爬**：真实信源若有反爬，需要自己加 header 或换信源
4. **没有去重跨天**：同一事件连续两天出现会重复进日报。跨天去重需要做事件聚类，超出当前范围

## 设计原则（写给想改这个项目的人）

- **prompt 是一等公民**，放在 `prompts/` 而不是塞进 Python 字符串里。改 prompt 不需要碰代码
- **降级的每一步都要能跑**：LLM 调用失败自动回退规则模式，信源挂了只跳过该源不中断
- **产出的每一条都能溯源**：没有来源链接的条目宁可不写
- **承认不知道**：判断不了影响就标 `watch`，不要为了填满日报硬凑结论
