# 需求拆解工作台 · Requirement Triage

把一堆零散的业务诉求，收敛成"先验证哪一块"的结论。

**在线试用**：下载 `index.html` 双击打开即可（无需 npm、无需服务器、无需联网）。

---

## 它解决什么问题

需求池里堆着几十上百条诉求，每条颗粒度都不一样——有的一句话，有的一页 PPT。这时候**逐条排期是错误姿势**：颗粒度不齐的清单没法比较，排出来的优先级全凭感觉。

正确顺序是三步：**先聚类 → 看分布 → 选验证域**。这个工具把这三步做成可执行的流程。

## 五步走完

| 步骤 | 你做什么 | 工具给你什么 |
|---|---|---|
| 1 · 输入 | 粘贴需求清单（每行一条，支持 `描述,部门,频次`） | 自动拆字段、猜部门 |
| 2 · 打标签 | 一键解析 | 需求类型（问答 / 处理 / 生产 / 协作 / 管理）+ 依赖能力 + 频次 |
| 3 · 看分布 | 无需操作 | 纯问答 vs 需能力编排的占比、能力依赖 Top、部门 × 类型交叉表 |
| 4 · 定验证域 | 给候选域打四个维度的分 | 总分 + 建议（验内核 / 验边界 / 暂缓）+ 结论文字 |
| 5 · 导出 | 点按钮 | 台账 CSV、分析报告 Markdown、结构化 JSON |

## 规则引擎怎么打标签

关键词命中最多者胜出（`RULES` 数组，直接改代码即可调）：

| 类型 | 依赖能力 | 典型关键词 |
|---|---|---|
| 处理型 | OCR/解析 | 扫描、识别、发票、抽取、结构化 |
| 处理型 | 问数/计算 | 报表、汇总、统计、核算、台账、指标 |
| 生产型 | 生成/模板 | 生成、起草、模板、报告、摘要、批量 |
| 协作型 | 协作/流程 | 共享、审批、任务、跟进、会签、流转 |
| 管理型 | 权限/配置 | 权限、角色、后台、配置、账号、审计 |
| 问答型 | 检索/问答 | 查、找、问、怎么、制度、流程、规定 |

没命中任何关键词时：长句（>26 字）归协作型，短句归问答型。

**规则引擎只负责初筛，判断在人手里**——台账里每条需求的类型都可以下拉手动修正，改完统计实时重算。

## 验证域评分模型

四个维度各 1-5 分，满分 20：

| 维度 | 在问什么 |
|---|---|
| 需求密度 | 这个域的诉求够不够多 |
| 流程封闭度 | 场景能不能自闭环地验证 |
| 数据可得性 | 材料/数据拿不拿得到 |
| 改动成本 | 动它贵不贵（分越高越便宜） |

判读：**≥16 验内核**（需求密、流程封闭、改动便宜，适合验证核心假设）｜**12-15 验边界**（专门探能力边界）｜**<12 暂缓**。

## 为什么这么设计

| 决策 | 理由 |
|---|---|
| **用规则引擎，不调大模型** | 分类规则要可解释、可复现、可人工修正。LLM 分类看起来聪明，但改一条规则要重写 prompt，且结果不可复现 |
| **单文件 HTML，零依赖** | 双击即用、离线可用、能直接发给别人。PM 工具的传播成本比技术先进性更重要 |
| **不在浏览器里存数据** | 需求是公司内部信息。数据只在当前标签页，刷新即清空，不留痕 |
| **类型可人工修正** | 见上。工具给初筛，判断归人 |
| **导出优先于展示** | 屏幕上好看没用，能拿去评审的 CSV/Markdown 才是产出物 |

## 已知局限

- 关键词规则对**长句多意图**的需求（比如"识别发票并生成台账"）只能归一类，需人工拆条
- 部门靠关键词猜，未命中显示"未标注"，建议在输入时显式带上
- 频次默认"中"，真实使用建议导入时标注

## 与方法论案例的关系

`docs/01-需求拆解与场景验证/` 是这套方法论的**文字版**，这个工具是**可执行版**。示例数据 41 条跑出来是 29.3% 纯问答 / 70.7% 需能力编排——与案例里的真实分布（29.6% / 70.4%）接近，可对照阅读。
